知识存储 · 精炼学习笔记

目标：快速抓住图数据库 / Neo4j / RDF 存储的核心，能说清「知识存在哪、怎么查、和表示层如何对应」。

一句话总览

知识存储 = 把已获取的实体与关系持久化，并提供高效查询 / 遍历 / 更新能力。

要点 本质 强项
图数据库 用「节点 + 边」原生存图 多跳关联、路径查询
Neo4j 主流属性图引擎（Bolt + Cypher） 工程成熟、生态好、本项目在用
RDF 存储 用三元组存语义网数据 标准互操作、配合 OWL 推理

与上下游关系：

知识表示（定模式） → 知识获取（产实例） → 知识存储（落盘可查） → 推理 / 应用

选型口诀：业务应用与多跳查询优先属性图（Neo4j）；强语义互操作与 OWL 推理优先 RDF 库（也可并存）。

1. 图数据库（Graph Database）

核心定义

以图数据模型为第一公民的数据库：数据就是节点（Vertex）与边（Edge/Relationship），查询围绕遍历与模式匹配展开。

为什么 KG 爱用图库

对比 关系库（表） 图数据库
关联表达 外键 / JOIN 边一等公民
多跳查询 JOIN 爆炸、难写 沿边走 N 跳自然
Schema 表结构较刚性 标签/属性更灵活（仍建议有约定）
典型问题 「谁控股谁的子公司的…」要多层 JOIN MATCH (a)-[:CONTROLS*1..3]->(b)

知识图谱的本质是关联；图库把关联从「计算出来的」变成「存进去的」。

两种主流图模型

模型 基本单位 代表 适合
属性图（Labeled Property Graph） 带标签的节点 + 带类型的边，均可挂属性 Neo4j、JanusGraph（属性图模式） 业务系统、OLTP 图查询
RDF 图 (s, p, o) 三元组，资源用 IRI GraphDB、Jena TDB、Virtuoso 语义网、开放数据、OWL

本仓库采用 属性图（Neo4j）。

属性图三要素（务必熟）

  1. 节点 Node：实体，可有多个 Label（如 :Company）
  2. 关系 Relationship：有向边，有 Type（如 BELONGS_TO），通常不能没有起点/终点
  3. 属性 Property：节点或边上的键值（name、code、ratio…）
(贵州茅台:Company {name:"贵州茅台"})
    -[:LISTED_AS]->
(600519:Stock {code:"600519"})

图库核心能力速记

  • 模式匹配：找符合形态的子图
  • 路径/多跳：控股链、竞品二度关系
  • 聚合统计：某行业下公司数、某文档提及实体数
  • 约束与索引：唯一性、查得快

速记

  • 图数据库回答：「点边怎么存、关联怎么查」
  • 选型先问：查询是否以多跳关系为主？是 → 优先图库

2. Neo4j

核心定义

Neo4j 是基于属性图的图数据库；应用通过 Bolt 协议连接，用 Cypher 声明式查询语言读写。

工程三件套

组件 作用 本项目对应
Neo4j Server 存数据、执行 Cypher Docker / 本地实例，7687 Bolt，7474 Browser
Bolt Driver 应用连接池与会话 neo4j-driver，backend/src/db.ts
Cypher 增删改查与图模式 backend/src/services/kg.ts

连接直觉：

App  --Bolt-->  Neo4j
       URI: bolt://localhost:7687

Cypher 最小必备

-- 创建/合并节点（有则复用，无则创建）
MERGE (c:Entity:Company {name: $name, entityType: 'Company'})
ON CREATE SET c.id = $id, c.createdAt = datetime()

-- 创建关系
MATCH (a:Entity {name: $from}), (b:Entity {name: $to})
MERGE (a)-[r:BELONGS_TO]->(b)

-- 查询子图
MATCH (n:Entity)-[r]->(m:Entity)
WHERE n.name CONTAINS $keyword
RETURN n, r, m

-- 多跳（示例：最多 3 层控股）
MATCH path = (a:Company)-[:CONTROLS*1..3]->(b)
RETURN path
关键词 含义
MATCH 匹配已有模式
MERGE 匹配不到就创建（幂等入库常用）
CREATE 直接创建（易重复，慎用）
SET / DELETE / DETACH DELETE 改属性 / 删边或节点
RETURN 返回结果

约束与索引（生产必想）

CREATE CONSTRAINT entity_id IF NOT EXISTS
FOR (n:Entity) REQUIRE n.id IS UNIQUE
  • 唯一约束：防止重复业务键
  • 索引：加速 WHERE name = … 等查找
    本项目在 ensureConstraints() 中创建 Entity.id 唯一约束。

会话与事务（Driver 用法要点）

Driver（进程级单例）
  └─ Session（一次逻辑工作单元）
       └─ Transaction（读写事务，可批量 MERGE）
  • 读多用只读会话/查询；写用 executeWrite
  • 同一 Session 不要并行跑多条查询（易报错）
  • LIMIT 等整数参数应用 neo4j.int()（本项目已处理）

本项目落库模型（钉在代码上）

设计 说明
统一标签 :Entity 便于「查全部实体」
类型标签 :Company / :Stock … 便于按类过滤
属性 entityType 与标签双轨，方便应用层
业务键 name + entityType MERGE 去重依据之一
文档 :Document + MENTIONS 溯源：知识从哪篇文档来 
(:Document)-[:MENTIONS]->(:Company)-[:LISTED_AS]->(:Stock)
                              └[:BELONGS_TO]->(:Industry)

对应代码：ingestExtractedGraph / getGraph / searchGraph（backend/src/services/kg.ts）。

Neo4j 与「知识表示」如何对应

表示层概念 Neo4j 落地
类 Class Label / entityType
个体 Individual Node
对象属性 Relationship Type
数据属性 Property
公理（唯一、基数等） Constraint + 应用校验（完整 OWL 推理不在 Neo4j 内核）

速记

  • Neo4j 回答：「属性图怎么工程化存与查」
  • 入库优先 MERGE + 约束，查询优先 模式匹配与多跳

3. RDF 存储

核心定义

以 RDF 三元组（及可选具名图）为存储单位的知识库，常用 SPARQL 查询；可与 RDFS/OWL 推理器配合。

<http://example.org/sec#Moutai>
    <http://example.org/sec#listedAs>
        <http://example.org/sec#S600519> .

和属性图存什么不一样

Neo4j 属性图 RDF 库
标识 内部 id + 业务属性 全局 IRI
边 可直接挂丰富属性 边属性常需「再化」（空白节点/中间资源）
查询语 Cypher SPARQL
类型 Label rdf:type
推理 规则/插件/应用层 常原生接 RDFS/OWL 推理
交换 专有/导出 标准 Turtle/RDF-XML/JSON-LD

「边也要有属性」（如持股 12%）时：

  • 属性图：(a)-[:HOLDS_SHARE {ratio:12}]->(b) 很自然
  • RDF：往往引入中间节点或 RDF-star 等扩展

常见 RDF 存储形态

形态 说明
三元组库（Triple Store） GraphDB、Jena TDB、Blazegraph、Virtuoso…
文件/数据集 .ttl / .nt 批量交换（如 md/examples/securities-mini.ttl）
混合架构 Neo4j 服务在线查询 + RDF 做发布/对齐/推理

SPARQL 最小对照

PREFIX : <http://example.org/sec#>

SELECT ?company ?stock WHERE {
  ?company a :ListedCompany ;
           :listedAs ?stock .
}

约等于 Cypher：

MATCH (company:ListedCompany)-[:LISTED_AS]->(stock:Stock)
RETURN company, stock

何时选 RDF 存储

  • 需要与外部语义网数据集互联互通
  • 需要较完整的 OWL 一致性检查 / 分类推理
  • 数据以开放标准发布（政府、百科、科研 KG）

何时仍用 Neo4j：

  • 证券投研/风控等业务应用、可视化、高并发点查与多跳
  • 团队更熟属性图与 Cypher（本仓库路线）

速记

  • RDF 存储回答：「用标准三元组把知识存成可交换、可推理的网」
  • 文件里的 OWL/Turtle 是「可交换的知识」；RDF 库是「可查询的三元组服务」

5 分钟自测

  1. 为什么知识图谱常用图数据库而不是只靠关系表？
  2. 属性图的三要素是什么？本项目 Entity + Company 双标签用意？
  3. MERGE 和 CREATE 在入库时有何区别？
  4. Neo4j 的 Bolt / Cypher 各是什么角色？
  5. RDF 存储与 Neo4j 怎么选？边属性场景谁更省事？

参考答案要点：
①多跳关联是一等公民
②节点/关系/属性；统一扫描 + 按类型过滤
③MERGE 幂等，CREATE 易重复
④Bolt 连接协议，Cypher 查询语言
⑤业务多跳用 Neo4j，语义互操作/OWL 用 RDF；边属性属性图更直接

建议学习顺序

  1. 搞清 属性图 vs RDF 图（先选型观）
  2. 在 Browser 里手写 10 条 Cypher（MERGE/MATCH/路径）
  3. 对照本仓库 kg.ts 看 Driver 会话与入库
  4. 打开 securities-mini.ttl，对比「同一知识」的 RDF 写法
  5. 需要推理/开放数据时再深入 SPARQL + RDF 库
